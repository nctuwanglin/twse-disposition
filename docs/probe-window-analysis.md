# 分析任務：證交所處置公告的發布時間窗

這份是給「2026-10-05 排程代理」看的任務書。代理從零開始、沒有任何對話脈絡，
所有需要的背景都寫在這裡。**只做分析與回報，不要修改任何檔案、不要開 PR、
不要 push。**

## 背景

這個 repo 產生台股「處置股」儀表板，由 `.github/workflows/update.yml` 每個
交易日自動抓取證交所（TWSE）與櫃買（TPEx）資料、重繪 `index.html`、發佈到
GitHub Pages。

2026-09 的一次調查回推 55 天的歷史快照，發現 **59 筆處置公告在公告當天沒有
被收錄、隔一個交易日才出現**，而且高度偏向證交所（TWSE 漏 52 筆、TPEx 只漏
7 筆）。這些公告的處置起始日幾乎都是次一交易日，等於使用者從未在生效前看到
它們。

原因之一已於 2026-09-21 修好（見 commit `87c2a34`）：舊版在「報價資料日沒比
上次新」時會整班早退，連公告都不抓，所以第二班形同失效。現在每班都會抓。

**但還有一個未證實的問題**：證交所的公告到底幾點才真的取得到？如果它晚於
所有排程時段才發布，那麼即使每班都抓也還是當天抓不到。這份分析就是要回答
這個問題。

## 資料來源

### 主要：`data/probe_log.jsonl`

`scripts/probe_announcement_sources.py` 每次執行追加一行 JSON。欄位：

| 欄位 | 意義 |
|---|---|
| `at_utc` / `at_tpe` | **實際執行時刻**（UTC / 台北）。GitHub 排程延遲數小時是常態，名目 cron 時間沒有參考價值，一律以這個為準 |
| `tpe_date` | 執行當下的台北日期 |
| `openapi` | 現用端點 `openapi.twse.com.tw/v1/announcement/punish`（無日期參數）的結果 |
| `rwd` | 對照端點 `www.twse.com.tw/rwd/zh/announcement/punish`（支援 `startDate`/`endDate` 前瞻查詢）的結果 |

`openapi` / `rwd` 內各有：

- `rows`：抓到的處置公告筆數（只計 4 碼一般股票）
- `forward`：**未生效公告筆數**（`period_start > 當天`）。這是關鍵指標——
  大於 0 代表此來源在該時刻已經能提供「即將被處置」的前瞻資料
- `max_ann`：看到的最新公告日期
- 失敗時則為 `{"error": "..."}`

### 次要：`data/last_counts.json` 的 git 歷史

每次正式更新會寫入 `announcement_asof`（該次抓到的最新公告日）。用
`git log -p -- data/last_counts.json` 可以看出**每次正式排程實際看到的公告
進展到哪一天**，與 probe 互為佐證。

## 目前的排程（UTC cron，台灣 = UTC+8）

`.github/workflows/update.yml`：
- `37 9 * * 1-5` → 名目台灣 17:37（主跑）
- `17 12 * * 1-5` → 名目台灣 20:17（補跑）

實測因 GitHub 排程延遲，這兩班常落在**台灣時間約 21:47 與約 00:40**。

`.github/workflows/probe.yml`（純診斷，四個時段）：
- `30 23 * * 0-4` → 名目台灣 07:30
- `0 3 * * 1-5` → 名目台灣 11:00
- `0 9 * * 1-5` → 名目台灣 17:00
- `0 12 * * 1-5` → 名目台灣 20:00

## 要回答的問題

1. **公告時間窗**：以 `at_tpe` 為橫軸，`forward` 由 0 變正、或 `max_ann`
   往前推進，最早出現在**台北時間幾點**？逐交易日列出，看是否穩定。
2. **兩個端點有差嗎**：同一時刻 `openapi` 與 `rwd` 的 `forward` / `max_ann`
   是否不同？若 RWD 明顯更早拿得到前瞻資料，那才是該換端點的證據。
3. **現有排程夠不夠**：把「實測落點約 21:47 / 00:40」與上面的時間窗對照，
   兩班是否已經涵蓋？若已涵蓋，就**不需要**改排程。
4. **probe 可以停了嗎**：資料是否足以定案？（樣本太少或結論不穩就說「還要
   再收」，不要硬下結論。）

## 分析注意事項

- **只看實際執行時刻**（`at_utc` / `at_tpe`），不要用 cron 名目時間推論。
- 排除 `error` 的紀錄，但要回報失敗比例——若某時段一直失敗，本身就是訊號。
- 週末與國定假日不會有新公告，分析時要排除，否則會稀釋結果。
- 樣本可能很少（每個交易日約 4–6 筆）。**寧可說「資料不足以定案」，也不要
  用少數幾筆硬推出時間窗。**
